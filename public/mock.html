Section 3 — Common Enterprise API Pain Points
Rate Limits
TPM (tokens/min) and RPM (requests/min) are separate. Check usage dashboards. Exponential backoff on 429s. Limit increase requests need business justification.
Context Window
200K token limit. Prompt engineering (compression, summarization) vs chunking vs product limitation. Token counting must be accurate — use the tokenizer, not estimates.
SSO / SAML Failures
Certificate mismatch (most common post-rotation). Clock skew >5 min. Wrong ACS URL. NameID format mismatch. Okta: attribute statements. Azure AD: claim mapping. Google Workspace: entity ID.
Response Quality / Safety
(1) Prompt engineering fix — customer can resolve. (2) System prompt issue — customer config. (3) Constitutional AI behavior — model as designed. (4) Genuine regression bug — escalate with repro.
Streaming Timeouts
Exact round-number timeouts (30s, 60s) = infrastructure defaults. Check load balancer idle timeout, HTTP client timeout, proxy keep-alive settings.
Study Priority Guide
Troubleshooting Scenarios Highest Priority
The technical interview will almost certainly include a live troubleshooting scenario. You need to be able to walk through a diagnosis out loud, in order, without prompting. Practice narrating your thinking — not just knowing the answer.
Be ready to debug all of these:
SAML / SSO Failures
Certificate mismatch after IdP rotation → check SP cert. Wrong ACS URL → verify SP metadata. NameID format mismatch → compare IdP config. Clock skew >5 min → check server time sync. Always pull IdP logs + capture HAR trace.
Rate Limits (429 / 529)
Distinguish TPM vs RPM exhaustion. Check usage dashboard. Advise exponential backoff with jitter. For 529 (overload): same pattern. Limit increase requires business justification. Never tell the customer to just retry without backoff.
Private VPC / Network Failures
Firewall egress rules open but still failing → next suspect is SSL inspection / MITM proxy breaking TLS. Then: DNS resolution inside the VPC. Then: IP allowlisting. Then: streaming timeout at the load balancer (exact round-number timeouts = infrastructure defaults).
RAG Pipeline Quality Issues
Customer says Claude is "making things up." First question: what are you retrieving? Hallucination in RAG is almost always a retrieval problem — wrong chunks injected. Check: chunking strategy, embedding quality, retrieval relevance scoring, context window usage (too many docs = noise).
Context Window / Token Errors
Customer hitting limit on prompts that worked before → prompts grew, or conversation history isn't being truncated, or token counting is wrong. Solutions: summarize history, chunk input, tighten system prompt. 200K is the limit — it hasn't changed.
Streaming Timeouts
Times out at exactly 30s or 60s → always an infrastructure default, not a model issue. Check: load balancer idle timeout, HTTP client timeout, proxy keep-alive settings. Fix: increase timeout config or switch to chunked responses if timeout is unchangeable.
500 Internal Server Errors
Check status page first. Then: is it reproducible or intermittent? Minimal repro to isolate if it's prompt-specific. Capture full request + response + headers + timestamp. File internal bug only after confirming it's reproducible and not a customer-side issue.
LLM Concepts Explain to Non-Technical Stakeholders
You will need to explain these concepts clearly to enterprise stakeholders who are not engineers. Practice plain-language versions of each. The test is: could a VP of Sales understand your explanation?
Hallucination
Not a bug — an inherent property of LLMs. The model generates statistically likely text, not verified facts. Plain-language framing: "Claude is very confident but not always right. The fix is grounding it with real data — RAG, citations, or restricting what it's allowed to answer." Never dismiss a customer complaint about this without offering a real mitigation path.
Context Window
The model's working memory for one request. Everything — system prompt, chat history, retrieved docs, and the response — must fit within 200K tokens. Plain-language framing: "Think of it like RAM. If you put too much in, things get dropped or the request fails." Common fix: summarize history, reduce system prompt, chunk input documents.
RAG (Retrieval-Augmented Generation)
Solve the problem of Claude not knowing your private data or recent events. At query time, retrieve relevant documents and inject them into the prompt. Plain-language framing: "We search your knowledge base, grab the relevant pages, hand them to Claude along with the question, and Claude answers from what it just read." Failure points: retrieval quality, chunk size, context window usage.
Temperature
Controls randomness. Low (near 0) = consistent, deterministic. High (near 1) = creative, varied. If a customer complains about inconsistent outputs, temperature is often the cause. If they need reliable structured output (JSON, classification, extraction), advise temperature 0.
System Prompt
The operator's instruction set at the top of every request. Defines Claude's persona, constraints, context, and output format. Most enterprise "model quality" issues are actually system prompt issues — too vague, too long, conflicting instructions, or missing format guidance. Always ask to see the system prompt before escalating.
Fine-Tuning vs. Prompting
Fine-tuning retrains the model permanently on custom data — expensive, requires labeled data, not available to most Claude customers. Prompting (system prompts, few-shot examples) steers behavior at runtime — much cheaper, faster to iterate, and sufficient for 95% of enterprise use cases. Redirect customers asking about fine-tuning to prompt engineering first.
API Fundamentals Know Cold
These are the building blocks you'll use in every technical conversation. You should be able to explain any of these concepts without hesitation, and use them fluently when diagnosing issues.
HTTP Status Codes
2xx = success. 3xx = redirect. 4xx = client error (their problem): 400 bad request, 401 no auth, 403 no permission, 404 not found, 429 rate limited. 5xx = server error (our problem): 500 internal error, 529 overloaded. Rule of thumb: 4xx = customer can usually fix it; 5xx = file a bug.
401 vs 403
401 = "I don't know who you are" — missing, invalid, or expired API key. 403 = "I know who you are but you can't do that" — valid key but wrong scope or access-controlled resource. In practice: 401 = rotate or provide the key; 403 = check permissions and scopes.
OAuth
Authorization framework (not authentication). User grants a third-party app scoped access to their resources without sharing credentials. Flow: user authorizes → auth server issues access token → app uses token to call the API. Key concepts: access tokens, refresh tokens, scopes, grant types. SSO commonly runs on top of OAuth + OIDC.
Rate Limiting: TPM vs RPM
TPM = tokens per minute (total token throughput, input + output). RPM = requests per minute (number of API calls regardless of token count). Both can be hit independently. A customer sending many small requests can hit RPM while staying under TPM. A customer sending large prompts can hit TPM with just a few requests.
HAR File
HTTP Archive — a browser DevTools export of all network requests, responses, headers, and timing. Ask for one when diagnosing SSO failures, browser-based integration issues, or intermittent errors that are hard to reproduce. It gives you the raw HTTP conversation the browser actually had, which is often very different from what the customer describes.
Webhooks
HTTP callbacks — instead of polling "anything new?", the server POSTs to your URL when an event fires. Common failure modes in enterprise: firewall blocking inbound POST requests, SSL certificate errors on the receiving endpoint, endpoint timeout too short (webhook delivery retries until it times out). Always confirm the endpoint is publicly reachable before anything else.

Behavioral Stories Prepare STAR Format
Have a specific, real story ready for each of these. Vague answers get pushed on. If you can't name the account, the company, the outcome, or the quarter — you don't have the story ready. STAR: Situation → Task → Action → Result.
Named Account Ownership
Your story needs: what were the stakes of the account, how did you build trust over time, what kinds of technical issues came up, how did you coordinate with the CSM/AE, and what was the measurable result (retention, expansion, CSAT, uptime). This is the core story for this role.
Escalation to Engineering
Show: you did the diagnostic work before escalating, you packaged it well (repro steps, business impact, priority rationale), you stayed on the thread and kept the customer informed, and you closed the loop. The key thing they're testing: are you a filter or a relay?
Building From Scratch
Show: you identified the gap, involved stakeholders early, built something durable (documented, handoff-ready, not just in your head), and iterated on real cases rather than theory. This directly maps to the "new function" expectation in this role.
Disagreeing With Engineering
Show: you had a legitimate reason backed by customer impact data, you raised it professionally, you either changed the outcome or committed cleanly once the decision was made. Do NOT make engineering the villain. The best answers show you can advocate strongly and still collaborate.
A Mistake That Affected a Customer
They want: ownership (no deflecting), root cause understanding, fast recovery, and a process change so it doesn't repeat. The worst answers minimize the impact or blame someone else. The best answers are specific, show accountability, and end with what you permanently changed.
Why Anthropic / Why Now
Three-part answer: (1) genuine mission alignment — what specifically about AI safety resonates with you and why, (2) product excitement — what specifically about Claude or this customer surface is interesting, (3) career timing — why Support Engineering at a frontier AI lab at this point in your career is the right next move, not just a good one.
